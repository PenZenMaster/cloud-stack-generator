# Checkpoint: 2025-11-12_1419

## Context Summary

This session focused on implementing a complete backlink satellite site architecture for the cloud-stack-generator project. The goal was to enable CloudFront-hosted sites to function as independent SEO assets that provide backlink value to main production websites, rather than being ignored as duplicates by search engines.

**Why This Matters**: The user identified that the generated CloudFront site (https://dslmqk0s3vj23.cloudfront.net/) was intended as a backlink site to boost the main production site (https://restroomrentalsvirginia.com/). However, the system was configured incorrectly:
- Canonical tags pointed to main site → Google treated CloudFront as duplicate
- Sitemap contained main site URLs → Google indexed main site only
- No strategic backlinks present → Zero SEO value

This session fixed the entire architecture to enable proper backlink functionality.

## Design Variations & Rationale

### Backlink Site Architecture

**Design Decision**: Use conditional rendering in templates rather than separate template files for backlink sites.

**Rationale**:
- Single source of truth for templates
- Easy to maintain and update
- No template duplication
- Clear separation via configuration
- Backward compatible (defaults to main_site type)

**Alternative Considered**: Separate template set for backlink sites.
**Why Rejected**: Would create maintenance burden, code duplication, and increase complexity.

### Canonical URL Strategy

**Design Decision**: Implement `_get_canonical_base_url()` method in each generator rather than global utility.

**Rationale**:
- Each generator has access to its own config
- No cross-dependencies between generators
- Clear, self-contained logic
- Easy to test and debug

**Alternative Considered**: Global URL resolution utility function.
**Why Rejected**: Would require passing config through many function calls, reducing clarity.

### Strategic Backlink Placement

**Design Decision**: 4-5 strategic backlinks per page placed in natural content flow.

**Rationale**:
- Follows Google Webmaster Guidelines
- Provides genuine user value
- Avoids PBN (Private Blog Network) penalties
- Natural anchor text variation
- Contextually relevant placement

**Alternative Considered**: More aggressive linking (10+ links per page).
**Why Rejected**: Would appear spammy, risk manual action from Google, poor user experience.

### IAM Policy Scope

**Design Decision**: Grant broad S3 permissions (all buckets) but restrict to S3 only.

**Rationale**:
- Allows creating new client buckets programmatically
- Maintains security (no IAM, EC2, Lambda access)
- Follows least-privilege principle at service level
- Enables low-friction deployment workflow

**Alternative Considered**: Restrict to specific bucket names.
**Why Rejected**: Would require IAM policy updates every time a new client is added.
