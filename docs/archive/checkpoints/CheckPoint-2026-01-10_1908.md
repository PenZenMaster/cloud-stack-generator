Session focused on investigating and resolving GitHub issue #18: "Header Image and Logo Missing from AWS Deployed Website". User reported that CloudFront deployments were returning 403 Access Denied errors for header images and logos, while preview functionality worked correctly.

## Accomplishments

### 1. Root Cause Analysis - Bucket Policy Conflict (v3.6.2)
- **Issue**: CloudFront Mode B deployments returned 403 errors for all image assets
- **Root Cause**: Deployment code unconditionally called `configure_public_website()` for BOTH Mode A and Mode B
- **Problem Flow**:
  1. `configure_public_website()` made bucket public with `Principal: "*"` policy
  2. CloudFront OAC setup then replaced policy with CloudFront-only access
  3. Policy conflict and race condition caused 403 errors
- **Impact**: All Mode B deployments had broken image loading

### 2. Implemented Two-Part Fix
- **Commit 2587b8a**: Fixed bucket policy conflict
  - Made bucket configuration conditional based on deployment mode
  - Mode A: Calls `configure_public_website()` (unchanged)
  - Mode B: Skips public configuration, lets OAC handle permissions
  - Result: CloudFront URLs now accessible (403 errors resolved)

- **Commit ae1bb02**: Added explicit public access blocking
  - User testing revealed public access blocks were not enabled
  - Added explicit public access block configuration after OAC setup
  - Includes clear logging and error handling
  - Result: Buckets now properly secured with all 4 blocks enabled

## Design Variations & Rationale

### Public Access Block Timing

**Decision**: Enable public access blocks AFTER CloudFront distribution creation and OAC policy application

**Rationale**:
- OAC policy must be in place before blocking public access
- Ensures bucket policy grants CloudFront access via OAC
- Then blocks all other public access attempts
- Original code tried to do this in `update_bucket_policy_for_oac()` but had silent error handling
- New approach: explicit blocking in deployment flow with visible logging

**Alternative Considered**: Rely on `update_bucket_policy_for_oac()` function
- **Rejected**: Silent exception handler (`except Exception: pass`) hides failures
- Led to inconsistent state: OAC policy correct but public blocks disabled

### Mode A vs Mode B Configuration Path

**Decision**: Completely separate configuration paths for Mode A and Mode B

**Rationale**:
- Mode A (S3 Static Website): Requires public bucket with public policy
- Mode B (CloudFront + OAC): Requires private bucket with OAC-only policy
- These are fundamentally incompatible configurations
- Attempting to transition from one to the other causes conflicts
- Clean separation prevents policy conflicts and race conditions
