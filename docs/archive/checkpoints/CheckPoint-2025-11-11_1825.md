## Design Variations & Rationale

### Facade Pattern for WebsiteGenerator
**Decision**: Keep WebsiteGenerator as a facade instead of removing it entirely.

**Rationale**:
- Maintains backward compatibility with existing UI code (main_window.py, yaml_builder.py)
- Provides stable public API for external consumers
- Allows gradual migration to WebsiteOrchestrator if desired
- Minimal code (83 lines) with clear delegation pattern

### Three-Layer Orchestration
**Decision**: Split orchestration into BuildPipeline, ContentCoordinator, and WebsiteOrchestrator.

**Rationale**:
- Each module stays under 500 lines (maintainability goal)
- Clear separation of concerns (build, content, orchestration)
- Easy to test in isolation
- Follows Single Responsibility Principle

### Re-export from Orchestration
**Decision**: Re-export GenerationResult and GenerationError from website_generator.

**Rationale**:
- Maintains import compatibility for existing code
- Avoids breaking changes across the codebase
- Clear that these types are part of the public API
